# 自动同步上游与网站发布

本仓库的 `.github/workflows/sync-upstream.yml` 每 6 小时检查一次
`Yilegendoflink/garrison-protocol` 的 `main`，使用 Ubuntu 24.04 和 Node.js 24。
也可以进入本仓库 Actions →「检查上游并自动更新网站」→ Run workflow 手动运行。
不修改博客仓库，不需要个人访问令牌（PAT）。

## 更新条件

1. 拉取完整上游历史，检查上游最新提交是否已包含在本仓库中；已包含则结束。
2. 在 Actions 临时工作区执行普通合并，保留本仓库联机扩展及历史。冲突时撤销合并，报告文件名，不选择任何一方覆盖。
3. 候选提交执行原项目构建、联机单元测试、四浏览器联机流程及 Pages 子路径静态入口检查。原生注入点变化也会阻止更新。
4. 全部成功后以普通 push 更新本仓库 `main`。只推送检查前的候选提交，构建产生的工作区变动不会提交。期间有人更新 `main` 导致历史分叉时，push 被拒绝，下一次重新合并检查。
5. 直接调用本仓库 Pages 工作流，检出候选提交的完整 SHA 后构建和发布。GitHub 的 `GITHUB_TOKEN` 自动 push 不会触发另一个 push 工作流，因此不能只依赖 push 发布。

原单机全量测试存在已记录的失败，自动同步不以这些历史失败作为门槛，也不代表全部原作机制已验收。普通 Pages 发布工作流仍只构建；联机回归在同步工作流中执行。

## 失败与恢复

没有新提交不发布；合并冲突、构建或联机检查失败不推送，也不发布。检查及文件名可在 Actions 日志和运行摘要查看。完成适配或人工解决冲突后，可重新运行同步。

合并推送和 Pages 部署不是一个事务。若合并已推送、随后 Pages 发布失败，线上仍是上次成功部署版本；修复发布问题后单独运行「自动构建并发布 GitHub Pages」。此时重新同步会判断上游已合并，不会代替重试 Pages。

仓库需允许 Actions 使用 `contents: write`，且 Pages 的构建来源为 GitHub Actions。
若 Actions 页面提示工作流被禁用（fork 的定时任务常见），先点击启用；仅把 Pages 来源切换为 Actions 并不等于启用了定时任务。
分支保护若要求 PR 或禁止机器人直推，会阻止此方案的推送，需要按仓库管理规则处理。
上游修改 `.github/workflows/` 时 GitHub 的令牌权限也可能拒绝自动推送；届时人工核对并合并。
GitHub 定时任务可能延迟；公开仓库连续 60 天无活动可能被 GitHub 暂停 schedule，需在 Actions 中重新启用。

## 联机服务器

该流程自动更新 GitHub Pages 静态网站，不远程重启 VPS。生产联机服务器需在房间结束后更新到同一构建版本，见 `multiplayer/README.md` 的生产服务章节。网站和服务器的规则指纹不一致时，联机入口会阻止连接；单机仍可使用新版本。避免自动重启清空正在游玩的内存房间。

本地验证同步规则（创建临时 Git 仓库，不访问远程）：

```bash
node --test multiplayer/tests/upstream-sync.test.mjs
```

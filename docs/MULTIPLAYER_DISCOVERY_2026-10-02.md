## 已确认与本轮实施

用户已授权列计划并完整实现，要求较丰富注释；此前未逐项指定的问题按已提出的建议落地。已确认：

- 2/3/4 人对应 Boss 3/5/7 倍，基准为当前单机默认血量（四人原表 × 0.75），按开局人数固定。
- 道中结束后，完美玩家才可联防；两名联防者串行接力，最终按敌人原来源扣原玩家生命。
- 联防敌人刷新出生状态，联防者保留战后状态；联防不增加盟约层数。
- 生命损失按敌人原表扣血值，各玩家单轮最多10点。
- 悬赏六项均为精英；悬赏、道具补给和战术运营均六项公共候选，玩家依次选且不能重复。
- 其它部分按原单机主体与此前建议：独立商店、公共地图/波次/禁用方案、轮选轮换、全员就绪、固定1倍速、淘汰后观战、独立地图共享Boss血量。

新增代码集中在 `multiplayer/`，原单机源码、根依赖和构建保持不变。入口为独立联机网页；正式回归结果在联机 README 与测试报告记录。

## 1. 初始目标与已经明确的需求

用户要求先理解仓库和术语、找出歧义，再开发。优先保持单机代码不变，使后续同步原仓库时容易合并。

- 网页客户端新增联机入口，输入 IP 和端口进入房间，支持 2–4 人。
- 玩家有可自定义头像；游玩中可发送表情，队友可见。
- 入房后选策略，各玩家策略不得重复。
- 精英敌人选择与道具补给改为公共的 6 项候选，多人依次选择，不可重复。
- 每位玩家独立生命值，归零淘汰。
- 道中漏怪由完美作战者进行额外兜底战斗；最多使用两位最快完成者。
- 用户已确认两名联防者串行接力：第一名 C 的漏怪再交给第二名 D；最终仍漏掉的敌人按原始来源分别扣 A/B 的生命，不扣联防者的生命。
- 两人时，双方道中战结束后再展开联防，一人的漏怪进入另一人的地图；用户本轮已确认接收者必须完美作战，不实时插入本道中战。
- 兜底后的剩余敌人决定最终生命损失；兜底击倒悬赏目标，奖金归兜底者。
- Boss 血量按人数使用 3／5／7 倍，共同累计剩余血量。用户本轮已确认基准为当前单机默认血量，即四人原表 HP × 0.75，不采用本地自定义倍率；人数对应关系与淘汰后的倍率政策待确认。
- 备战可以切换队友布阵视角；联防自动观战，一名联防者单视角，两名左右分屏。
- 战斗计算优先留在浏览器，服务端主要负责同步、共享状态与视角所需消息。

## 2. 术语对照与证据

| 用户用语 | 仓库对应概念 | 已查明的含义与限制 |
| --- | --- | --- |
| 策略 | `bandId`、`season.bandDataListDict` | 不是盟约；会影响起始生命、商店/卡池和各类玩法效果。要在选择结束后创建玩家会话，避免先生成商店再改策略。 |
| 派兵布阵、准备界面 | 会话 `phase='prep'` | 干员位置、朝向、技能、装备、布局召唤卡属于会话状态。不能把上一战的残留实体当成备战棋盘。 |
| 道中战斗 | 非最终 Boss 的常规战斗 | 有出怪队列、时间上限和漏失；当前单机结算会直接扣玩家生命。 |
| 精英敌人选择 | 可能是机变决策的“悬赏” | 尚待确认。当前首次悬赏是最高奖金精英 1 项 + 普通敌人 2 项；后续为领袖 2 项 + 零奖金源石虫，并非全是精英。 |
| 道具补给 | 机变决策 `equipment` | 免费获得装备。独立于商店购入、商店升级奖励、装备自己产生的奖励。 |
| 机变决策 | `bounty / equipment / tactical` | 第三类是“战术运营”。用户只明确前两类六选且互斥，不能自动把第三类也改成同一规则。 |
| 赏金怪物 | 携带 `bountyReward` 的敌人 | 当前击倒事件把奖金加入击倒者所在会话的 `nextRoundBonus`，下轮入账。道具的“自身完美作战领奖”与逐只击倒悬赏是两类规则。 |
| 兜底战斗 | 原表称“联防” | `common.gameTipsList` 明写只有完美作战者可联防、联防时盟约不继续叠加。用户已确认两名联防者串行接力，最终损失归原始漏怪玩家。 |
| 完美作战 | 建议定义：本道中阶段全部处理完，漏怪数为 0 | 需确认超时、未出场怪、衍生敌人是否影响资格，不能仅凭 `leaks===0` 判断超时也完美。 |
| 最快完成 | 建议用同步开战后的模拟结束帧/战斗耗时 | 网络消息抵达顺序不代表战斗快慢；当前单机有暂停/倍速，联机需约束。 |
| 生命值 | 玩家会话 `s.hp / maxHp` | 与干员 HP、Boss HP、资金、战斗部署费用、SP 分开。策略可能赋予不同初始生命。 |
| Boss 战 | 最终回合 `finalBossId` | 与悬赏池里的 BOSS 级敌人区分。当前只开放昆图斯、卢西恩、萨米的意志，不扩充抽取名单。 |

## 3. 当前实现中不能直接沿用的地方

1. `NativeSession.finishCurrentBattle()` 在道中结束立即扣血，单轮损失上限 `ROUND_LEAK_CAP=10`；联机须先等联防结果。
2. `NativeBattle.step()` 在漏失累计达到当前生命（结合单轮上限）时可提前结束；联机中可能被队友救回，不能先提前结束或宣布淘汰。
3. 漏怪通过 `commitExit(...reason:'leak')` 离场；现有 `leak` 表现事件不足以传送完整敌人状态，且 `s.events` 会裁剪，禁止拿它当可靠交接账本。
4. 单机战斗超时的结果把仍在场敌人的 `leak` 值加入损失；需要明确这些敌人是否也进入联防，以及尚未出场的队列如何处理。
5. 当前 `bountyDecisionOffers()` 固定三项且使用 1 精英+2 普通 / 2 领袖+1 虫的结构。抽六项需要独立规则，不能简单重复调用两次，零奖金虫也不能重复占多个候选。
6. `NativeSession.restore()` 校验决策候选恰好三项；联机需要独立存档封套、版本和恢复路径。
7. 原表已有 `mode_multi_*`，但它们会改变普通敌人倍率、首回合倍率、阶段表、决策路径和时限。用户要求主体沿用单机，不能仅切换 modeId 就认为符合要求。
8. 当前首次单人决策的源码强制选悬赏，后续随机三类；`BOUNTY_SYSTEM.md` 的概述写每次随机。联机应明确自己的规则，不能掩盖此差异。
9. 最终 Boss 单机默认 HP = 四人原表 HP × 0.75。3／5／7 倍若以不同基准计算，会相差三分之一；应同时存基准、人数、倍率和最终值。
10. `native-play.js` 没有导出会话/绘制接口，单机 UI 状态和事件循环是模块内闭包。不能通过导入它获取完整的可控联机界面。
11. 单机使用 30Hz 模拟，支持本地倍速/暂停、后台补帧。联机排行榜、共享 Boss 和联防必须统一模拟时间规则，并处理浏览器后台降速。
12. 已有 `playerId / teamPeers / teamTransport`，以及 `queueFangTransfer / receiveFangTransfer / applyTransferInbox`。这是信标转交的局部接口，不是已经存在的网络房间；可以复用其语义和去重机制。

## 4. 待确认的问题

### 必须先确定的战斗规则

- **Q1 Boss 人数：** 基准已确认是当前单机默认，即四人原表 HP × 0.75。3／5／7 分别对应 2／3／4 人吗？人数按开局人数还是进入 Boss 时的存活人数？
- **Q2 两人联防：** 已确认双方道中结束后展开，接收者必须完美作战。两人都漏怪时如何扣血仍待确认（没有联防资格者）。
- **Q3 两名联防者的分配与扣血：** 已确认串行接力，C 漏的再交 D，最终漏怪按原始来源扣 A/B。不得在交接 C→D 时把 `sourcePlayerId` 改为 C。没有完美者时的处理仍待确认。
- **Q4 联防状态：** 漏怪保留当前 HP、形态、护盾和技能进度，还是恢复成出生状态？联防者沿用道中结束时的干员 HP/SP/召唤物/部署费用，还是按原布阵重开？是否允许再次布阵？联防时是否采用原表“不继续叠盟约”？
- **Q5 损失计数：** 按敌人只数，还是原表 `lifePointReduce`？单轮最多扣 10 是否保留？超时敌人和衍生敌人是否交接、是否扣血？
- **Q6 共同 Boss 的战场和时限：** 每人独立地图共用 HP，还是两人同图？保留各自 `100+生命` 时限和漏怪扣秒，还是统一全队时限？半血/阶段转换须跟随公共血量，不能各自触发。允许 Boss 的回血/复活机制时也须统一记账。

### 决策、回合与资源

- **Q7 “精英敌人”具体指什么：** 是否就是现有悬赏？六项全部精英、还是保留早晚池但扩成六项？战术运营仍各自三选一吗？每轮类型全队统一抽取吗？
- **Q8 选择顺序：** 入房顺序、生命最低者优先，还是轮换？每人选一项后剩余候选丢弃吗？选策略是自由抢选还是依次选择，有无时限？
- **Q9 主体采用何种规则：** 除明确列出的差异，是否保留单机难度倍率、回合数、决策轮次、资金和各自商店库存？地图、波次、禁用盟约和 Boss 是否全队一致？房主的自定义波次/禁用方案是否作为全队配置？
- **Q10 淘汰与胜负：** 淘汰者留在房间观战、不再选择奖励/准备吗？剩一人继续吗？共享 Boss 被击破后淘汰者是否也计胜利？

### 连接与表现（可采用建议作为初版默认值）

- **Q11 房间：** 一服务端多房间（加入需要房间号）还是 IP+端口对应一个房间？建议支持创建/加入，房主设置难度与配置，至少两人才能开始，中途仅原玩家重连。
- **Q12 部署：** 主要局域网游玩还是公网跨网络？建议服务端同时提供联机静态页面和 WebSocket。HTTPS Pages 连接普通 `ws://IP:端口` 存在混合内容限制，公网应提供可用的 HTTPS/WSS 地址，不能只做表单就宣称支持。
- **Q13 头像与表情：** 建议头像支持内置选图+上传图片裁切；表情先用固定列表。原表只有启用的表情主题 ID，尚未确认图像素材可用。是否要求上传自定义表情？
- **Q14 就绪/暂停/断线：** 建议全体存活玩家准备后同步开战，准备后锁定布阵，可在开战前取消；战斗固定 1 倍速。断线先留重连窗口，超时政策须定，不应由观战者猜测结算。

## 5. 技术方案（建议）

### 独立目录与入口

建议新增 `multiplayer/`，内部包含 `client/`、`server/`、`shared/`、`tests/` 和独立 `package.json`。网页可从 `multiplayer/index.html` 进入；服务端用 Node.js 22+ 与 WebSocket（例如 `ws` 包，仅装在联机目录），不增加单机运行依赖。

联机网页通过 ES modules 导入现有 `dist/native-session.js`、`native-battle.js`、`runtime-data.js` 等规则模块，不复制干员、敌人、装备、盟约数值。服务端提供联机页面和允许访问的共享静态资源；部署时与原单机 `dist` 一起分发。原单机仍使用原 bundle，联机使用自己的启动/构建命令。

“原大厅里新增按钮”必然需要一个入口接入点。零改原文件的第一步可以是独立联机网址和联机启动页上的单机/联机入口；正式在原大厅加入按钮时，只做一个集中、可审查的入口改动，或在服务端提供的页面中注入入口。此取舍应公开记录，不以复制整个单机 UI 规避。

### 浏览器与服务端的职责

| 浏览器负责 | 服务端统一负责 |
| --- | --- |
| 自己的商店、干员/装备/技能、盟约、地图环境、逐帧战斗 | 房间成员、身份/重连、准备状态、配置与客户端规则版本一致性 |
| 战斗状态快照和可靠的漏怪/击倒/伤害报告 | 房间阶段、回合与开战时刻、轮流选择、已占用选项 |
| 队友快照的只读绘制、表情和头像展示 | 联防任务分配、敌人来源和交接次数、最终扣血及淘汰 |
| 联防战斗的实际模拟 | 悬赏结算去重、公共 Boss HP、回血/阶段/胜负的统一广播 |

服务端不运行整套战斗，但也不能只把客户端的任意 `hp` 相互转发。公共 Boss 用“实际作用于 Boss 的伤害增量”记账，不能上报整场总伤害（包含增援和过量伤害）。每条报告附 `room/run/round/battle/player/seq` 与稳定事件 ID；服务端验证身份、当前阶段和任务归属并去重，广播带递增版本的结果。

客户端权威战斗适合朋友间联机。服务端可检查消息边界、阶段、重复事件与不合理数值，但无法据此证明每次伤害确实由合法模拟产生。初版不把此架构描述为完整防作弊。

### 规则适配边界

用独立 `MultiplayerSession` 适配会话，隔离需要替换的“立即扣血”“决策三候选”“自主推进回合”“本地 Boss 判胜”等方法；必要时使用只作用于本局实例的战斗包装/适配，不全局修改 `NativeSession.prototype / NativeBattle.prototype`。

开始实现前需验证漏怪退出、所有伤害渠道和提前结束条件是否有足够接口。若零改原文件无法可靠覆盖某条规则，应记录具体缺口；新增小型通用接口与在联机目录复制大型引擎相比更容易跟随上游，但用户尚未授权放宽“不改原代码”的偏好。不要用动态改源码字符串或读取短命表现事件补规则。

观战只读取玩家发布的棋盘快照，不在每个浏览器另跑所有队友的战斗。准备快照包含部署位置、朝向、装备、技能、召唤布局；战斗快照包含可绘制实体、必要状态和模拟帧。对方的商店、手牌操作不能从观战 UI 发出。联防双视角分别保存独立快照。

建议从 5–10Hz 战斗快照和 30Hz 本地模拟开始实测；观战插值只用于表现。保留可靠的规则报告与可丢弃的画面更新两条语义，不每帧发送整个会话。

### 房间阶段草案

`waiting → strategy-selection → preparation → main-battle → collecting-results → support-battle（可跳过） → settlement → decision（按回合，可跳过） → preparation`

最终回合由 `preparation → shared-boss → finished` 进入共享 Boss 流程。淘汰者保持观战身份。当前哪些状态允许重连、何时停止个人计时、何时锁定决策，均由服务端阶段决定。

两名联防者已确认为顺序处理：`main-battle → collecting-results → support-C → support-D（C 无漏怪则跳过） → settlement`。最终按剩余敌人的原始来源逐位结算；第一段结束不能提前扣 A/B 的生命。双视角仍按用户要求显示，但两场战斗不是并行模拟；未开始或已结束一侧的具体呈现待 UI 设计确定。

验收例：A 漏出的敌人标为 A1–A6，B 漏出的敌人标为 B1–B4；C 处理后剩 A2、A5、B3，D 再处理后只剩 A5，则只有 A 承担 A5 对应损失，B 不因已被兜底击倒的 B3 扣血。损失按只数还是敌人原表扣血值见 Q5，不能在此例中预设。

漏怪交接记录至少包括 `enemyInstanceId / sourcePlayerId / round / enemyId / bountyReward / supportAssignmentId`；是否保留战斗属性由 Q4 决定。不能只传敌人种类和数量，否则混合来源无法正确扣血、悬赏也可能重复发放。

## 6. 开发与验收顺序

1. 确定 Q1–Q10，记录选择和可复核的具体例子，再冻结首版规则。
2. 独立服务端、连接页、2–4 人房间、头像、表情、策略不重复和就绪流程。
3. 接入单人规则的本地会话、备战观战、公共六候选轮选、阶段推进。
4. 完整实现漏怪交接、联防、扣血与淘汰、奖金归属、联防自动观战/双屏。
5. 接共享 Boss 的伤害/回血/阶段/结束广播，保留现有三名 Boss 机制范围。
6. 重连、浏览器后台、版本/配置不一致、运行部署文档和端到端验证。

关键验收必须包含 2/3/4 人、无/一/多名完美者、两人均漏、多来源混合漏怪、超时、联防再漏、零奖金虫、重复/重放报告、断线重连、Boss 同时致死/跨阶段，以及备战只读观战和左右联防视角。原单机回归也必须继续通过；仓库既有 `release:check` 的 pending 不等于本次新增失败，也不能因此宣称整体发布验收完成。

探索轮仅新增本文；实施轮增加独立 `multiplayer/`，未修改原单机源码、根依赖、构建脚本或发布流程。
